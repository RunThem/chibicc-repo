# 01 库概览, 定位与设计原则

## 1.1 一句话定位

`libcp` 把一个 C11 前端的四个中间表示层做成可复用的 C 库: 保真的 token 流, lossless CST, 忠实语法 AST, 以及 sema 标注树. 它不带编译器驱动器, 也不带 x86-64 代码生成器. 仓库里的 `chibicc` 二进制是这个库的参考消费者.

## 1.2 为什么需要这个库

上游 chibicc 是一个完整的教学编译器: 词法, 预处理, 语法, 语义和代码生成串成一个程序, 中间状态是文件域 static, 出错直接 `exit(1)`, 内存从不释放. 这种形态适合从头读到尾, 不适合被别的软件嵌入.

需要 C 前端的软件很多, 但它们要的往往不是"生成可执行文件":

- 格式化器要的是注释, 空白和原始拼写, 不要类型.
- C 转 C 的源到源工具要的是忠实于写法的语法树, 不要后端整形.
- linter 和静态分析器要的是名字绑定, 类型和常量结论, 不要汇编.
- 编辑器工具要的是宏展开来源和精确位置.

把它们全部绑在一个编译器上, 结果是要么复制一份编译器再裁剪, 要么直接调用编译器命令行并解析文本输出. 这两种做法都脆弱. 这个库的目标是把前端做成一组有明确输入输出契约的阶段, 让消费者按需取用.

## 1.3 库提供什么

按中间表示划分, 库对外提供四层能力, 外加一条横切的预处理:

| 层 | 能力 | 主要入口 | 产物 |
|---|---|---|---|
| 第 1 层 | 词法, 保留 trivia | `libcp_tokenize_file` / `_buffer` / `_buffer_len` | `LibcpToken` 链, 可逐字节重建输入 |
| 预处理 | 宏展开, 条件编译, include | `libcp_preprocess` | 展开后的 token 链 + provenance 链 |
| 第 2 层 | lossless 具体语法树 | `libcp_cst_parse` | `LibcpCstNode` 树, `CST_*` 55 种节点 |
| 第 3 层 | 忠实语法 AST | `libcp_parse` | `LibcpNode` 树, `ND_*` 69 种节点 |
| 第 4 层 | 语义标注 | `libcp_sema` | 原地标注的树 + `LibcpObj` 全局对象链 |

此外还有:

- `libcp_reconstruct`: 从第 1 层的 token 流重建原始字节.
- 宏展开 provenance 的 11 个访问器, 以及 `libcp_expansion_dump` / `_verify`.
- 一个不透明的 `LibcpContext`, 管理一个翻译单元的全部状态和内存.
- 一套可替换的分配器宏 (`<libcp/allocator.h>`).
- 10 个公共头, 38 个公共函数(L5 起含 `libcp_cst_seed_typedef` 与 `libcp_node_source_range`). 公共符号一律 `libcp_` / `Libcp` 前缀.

库的实现约 1.2 万行 C, 公共头约 2.3 千行. 它没有外部依赖, 除 C 标准库外只要求 POSIX 的文件与线程基础能力.

## 1.4 这个库不是什么

这一节和上一节同样重要. 把边界说清楚, 比把能力说大更有用.

- **不是编译器**. 库不生成汇编, 不调用汇编器或链接器, 不处理命令行. 仓库里的 `main.c` 和 `codegen.c` 不是库的一部分.
- **不是预处理器命令行工具**. 没有 `-E` 形式的公共输出函数. 要打印展开流, 消费者自己遍历 token 链并写文件.
- **不做优化**. 没有优化 pass. 第 5 层的代码质量不在库的承诺范围内.
- **不做错误恢复**. 第一个错误经诊断回调报告后, 当前公共入口立即返回. 没有"带错误继续解析"的部分树.
- **不是线程安全的单对象**. 一个 context 不能跨线程并发使用. 不同 context 可以在不同线程并存.
- **不承诺 ABI**. 公共结构体的字段直接暴露. 换字段就是换版本, 只保证源码兼容.
- **不是完整的 C 标准实现**. 不支持复数, K&R 风格函数原型, GCC 风格内联汇编; digraph 和 trigraph 有意不支持. 这些限制继承自上游.
- **不是增量解析器**. 没有语法树增量更新, 没有按编辑区间重解析.

## 1.5 设计原则

下面七条是理解代码形态的关键. 它们解释了为什么库分成现在这几层, 为什么一些看似可以合并的东西故意没有合并.

### 1.5.1 每层是一份数据契约, 不是一个函数调用栈

消费者拿到的是结构体树和链, 不是回调流. 库不会在解析途中"通知"消费者, 也不会要求消费者实现访问者接口. 这样消费者可以在树建好之后反复遍历, 用自己熟悉的算法处理, 不必把逻辑塞进回调.

代价是内存占用: 一棵完整的树和它的 token 同时存活. 库用 arena 管理, 不逐对象释放.

### 1.5.2 CST 建在预处理之前

预处理是不可逆的. 宏展开会丢掉调用点的拼写和布局, 条件编译会丢掉未选中的分支, `#include` 会丢掉指令本身和文件边界. 如果 CST 建在展开后的 token 流上, 就无法兑现"逐字节重建源文件"的承诺.

因此第 2 层从 `tokenize_file()` 的直接输出建树: 预处理指令是节点, `#if` 的每个分支都保留, 每个标点是显式叶子. 展开后的语法形态交给第 3 层, 宏展开的来源交给 provenance. 这三者各管一段, 不互相冒充.

### 1.5.3 语法层忠实于写法, 语义层只做标注

第 3 层保留源码的每一种写法区别:

- `a[i]` 是 `ND_SUBSCRIPT`, 不重写成 `*(a + i)`.
- `a > b` 是 `ND_GT`, 不交换操作数变成 `ND_LT`.
- `x += 1` 是带 `op` 的 `ND_ASSIGN`, 不展开成读改写.
- `while` 是 `ND_WHILE`, 不降级成 `ND_FOR`.
- 隐式 cast 有 `is_implicit` 标记, 与源码写出的 cast 区分.
- 初始化器保留为 `LibcpInitializer` 记录, 不拍平成赋值链.

第 4 层在此之上绑定名字, 计算类型, 求值常量, 布局聚合类型, 并把编译期结论记录在节点上. 它不改变源码写法.

这条原则的收益是: 源到源工具可以直接消费第 3 层, 不会看到"编译器内部优化后的形状"; 语义工具可以消费第 4 层, 不必自己重做类型系统.

### 1.5.4 后端整形不属于库

指针算术缩放, 复合赋值的读写回环, 自增自减展开, 关系运算符换序, 临时槽, 语句重排, 标签分配, 这些都是"为了发射某种机器码"而做的整形. 它们只允许出现在 `codegen.c`.

库层只保留语言规定存在的对象: 字符串字面量的匿名全局, 复合字面量的隐藏对象, ABI 参数区, 变参区, 返回缓冲的描述. 这些不是发射便利, 是 C 语言和 ABI 要求存在的东西.

这条红线不是口号, 有逐项审计: 第 5 层的整形遍只剩需要槽, 语句或标签的项, 其余在发射点就地处理. 详见第 8 章与 `plans/RESULT-codegen-direct.md`.

### 1.5.5 lossless 优先于方便

第 1 层保留每个 token 前的空白, 注释和换行, 以及 token 的原始拼写. token 的位置同时有扫描坐标和 raw 坐标两套. 这不是为了漂亮, 是为了让格式化器和重构工具能原样保留用户的代码.

CST 进一步把每个标点变成叶子, 保证叶子按序重建等于输入. 树的形状可以因为文法覆盖不全而退化, 但 token 一个都不能丢.

### 1.5.6 简单可读优先于巧妙, 性能靠后

上游的设计原则被保留下来:

- 解析器里的重复是有意的, 不用高阶函数或宏去消.
- 用链表当集合, 查找 O(n), 因为 n 通常很小.
- 一个 `Node` 结构体容纳所有节点类型的字段, 不做 union.
- 内存一律零初始化分配, 从不逐对象释放.

在这个库里, 这些选择还多了一层理由: 代码要被第三方阅读和修改. 聪明的抽象会提高修改门槛.

### 1.5.7 一个 context 对应一个翻译单元

所有 per-TU 状态收进 `LibcpContext`: 文件表, 宏表, 条件编译栈, 作用域, 语义状态, arena. 公共入口显式接收 context.

库层没有隐式上下文: 每个触碰 arena, 诊断, 格式化或 context 字段的内部函数以 `LibcpContext *ctx` 作为首参, 需要它的函数再把它传给调用者. 公共入口本来就把 context 作为首参. 契约是:

- 不同 context 可以在不同线程并存, 结构上互不可见.
- 同一个 context 不能跨线程并发.
- 诊断回调里可以创建, 使用, 释放另一个 context, 外层错误仍回到外层 context 自己的 frame.

`reset` 释放整个 arena 并清空 per-TU 状态, 保留配置. 所有由该 context 返回的指针在 reset 后立即失效. 这是库最重要的生命周期规则, 第 2 章会展开.

## 1.6 适用场景

| 场景 | 需要的层 | 能做什么 |
|---|---|---|
| 代码格式化 | 第 1, 2 层 | 保留注释与空白的重排, 不编译 |
| 重构 / codemod | 第 2, 3 层 | 按语法结构定位并改写源码片段 |
| C 转 C | 第 3 层, 或第 4 层 | 保留写法的源到源生成; 需要类型时用第 4 层 |
| linter | 第 3, 4 层 | 语法模式检查, 类型相关规则, 常量求值 |
| 静态分析 | 第 4 层 | 符号表, 调用关系, 结构体布局, 初始化数据 |
| 宏展开检查 | 预处理 + provenance | 追踪每个产物 token 来自哪次展开, 哪个实参 |
| 教学 / 实验 | 任意层 | 观察每个中间表示的形态 |
| 新后端 | 第 4 层 | 用自己的代码生成器替换 x86-64 |

## 1.7 不适用场景

- 需要完整的 C++ 或 Objective-C 前端.
- 需要诊断恢复, 在一份源码上报出全部错误.
- 需要跨翻译单元的链接期分析. 库只处理单个 TU, 不读目标文件.
- 需要稳定的二进制接口, 插到不同版本编译的宿主里.
- 需要高性能增量解析. 每次调用都从头构建.

## 1.8 关键术语

| 术语 | 含义 |
|---|---|
| 翻译单元 (TU) | 一个源文件加上它 include 进来的全部内容, 预处理后的整体 |
| context | 一个 TU 的容器. 持有 arena, 配置, 诊断回调和全部阶段状态 |
| trivia | token 之前被词法器跳过而不成 token 的字节: 空白, 换行, 注释, 续行 |
| raw 坐标 | 原始文件中的字节偏移, 未经换行归一, 续行删除或 universal char 改写 |
| 扫描坐标 | 词法器实际读取的缓冲中的偏移. 扫描缓冲是 raw 文本的派生 |
| CST | 具体语法树. 每个 token 和标点都是叶子, 预处理指令是节点 |
| 忠实 AST | 第 3 层的树. 保留源码写法, 不做类型, 不绑名字, 不求值 |
| 标注树 | 第 4 层处理后的树. 名字已绑定, 类型已计算, 结论已记录, 形状未改 |
| provenance | 宏展开来源链. 每个展开产物 token 携带一层或多层展开记录 |
| 物化 | 把语言规定存在的隐藏对象建出来, 如字符串的匿名全局 |
| 降级 / 整形 | 为发射服务的形状改写. 只允许在 codegen |
| 记录节点 | 解析器为声明产出的 `ND_DECL` / `ND_GVAR_DECL` / `ND_FUNCDEF` 等, 交 sema 消费 |
| 文法 oracle | 解析器唯一需要的语义反馈: 标识符是不是 typedef 名, tag 指向哪个类型 |
| 合成 token | 不是从源文件读出的 token, 如粘贴, 字符串化, 内建宏产物 |
| 第 5 层 | 仓库里的 `codegen.c`, 不属于库 |

## 1.9 与上游 chibicc 的关系

本仓库是 Rui Ueyama 的 chibicc 的 fork. 上游仍是一个教学编译器, 目标是让读者按 commit 学习 C 编译器怎么实现. 本 fork 保留了它的代码风格和大部分实现, 但把目标改成了库:

- 源码搬到 `libcp/src/`, 公共头在 `libcp/include/libcp/`.
- 根目录只留驱动器 `main.c`, 代码生成器 `codegen.c` 和驱动器内部头 `driver.h`.
- 所有跨层状态收进 `LibcpContext`, 错误改走诊断回调.
- 新增了 trivia, CST, provenance, 忠实语法层和 sema 标注层.
- 上游 README 描述的是编译器, 与本仓库冲突时以 `AGENTS.md` 和本文档为准.

上游的 C11 特性覆盖基本保留: 浮点与 long double, 位域, VLA, 复合字面量, 线程局部变量, 原子变量, 指定初始化器, 结构体按值传参与返回. 上游不支持的特性这里同样不支持, 见第 11 章.

## 1.10 成熟度, 承诺与风险

**已经做到的部分**:

- 阶段 5 的闸门全绿: Docker 内完整测试与自举, 汇编快照零 diff, 公共头独立编译, 符号白名单, ASan/UBSan 无报告, install 与 pkg-config 可用.
- 第 1 层到第 4 层的产物有逐字节或结构级锁定: trivia 48 个语料文件重建, CST 305 项断言, AST 85 例, 诊断 68 例, 形状 34 段.
- Pratt 表达式解析在成为唯一路径之前, 与旧级联的 AST 与汇编在 41 个语料文件和 tinycc 真实构建上逐字节一致 (PLAN-pratt-parse); 单一路径化后由汇编快照基线继续锁定.

**还没做到的部分**:

- L5 产品化验证未开工: 没有真实 formatter 消费者, 没有 AST 源码范围, 没有诊断展开点. 这意味着 API 的"手感"还没有被一个真实工具检验过.
- CST 的结构覆盖率不完整: 部分语料包含 `CST_UNPARSED`, GNU 语句表达式是主要来源. 重建不受影响, 但依赖结构的工具会退化.
- 公共结构体字段直接暴露, 版本升级可能破坏源码兼容.
- 性能没有优化, 大文件的内存峰值约为最终数据的两倍, 因为 arena 的 realloc 不回收旧块.

把这些写在最前面, 是为了让采用者按真实风险做决定, 而不是按"编译器前端库"的想象做决定.
